# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Automates creating expense-receipt PDF reports ("kvittomallar") for a student committee. Pulls submissions from a Google Sheet (backed by a Google Form), downloads the linked receipt images/PDFs from Google Drive, and generates one combined PDF per submission (cover page + attachments).

## Commands

```sh
python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt        # versions are pinned intentionally - keep them pinned

python -m kvittomall run               # fetch -> download -> process -> generate, in order
python -m kvittomall fetch             # Sheet -> data/responses.csv
python -m kvittomall download          # Drive links in data/responses.csv -> data/downloads/
python -m kvittomall process           # data/downloads/ -> data/processed/ (adaptive JPEG compression)
python -m kvittomall generate          # data/processed/ + data/responses.csv -> final/<category>/
python -m kvittomall handled           # toggle one row's reviewed state, or mark all unhandled rows handled
python -m kvittomall remove <row_key>  # delete on-disk file(s) for one row (never the CSV/DB) - --only downloads|processed|final
python -m kvittomall status            # read-only report of per-row/attachment state, no lock taken
python -m kvittomall webui             # local Flask control panel (dashboard + entries list) - see below
```

`docker compose up -d --build` (or `docker run <image> <command>`) is an alternative to the venv/`pip install` above, not a different way of running the code - see the "Docker is an alternative way to run this" note under Architecture for what `Dockerfile`/`docker-compose.yml` actually do.

`download`, `process`, `generate`, `handled`, and `run` all also accept an optional row-key argument to scope the action to a single row instead of every row (e.g. `python -m kvittomall generate "2026-01-01 10.00.00"`) - see the "scoped to one entry" note under Architecture.

```sh
pip install -r requirements-dev.txt                       # adds pytest + pytest-cov on top of requirements.txt
pytest                                                      # run the test suite (tests/, config in pytest.ini)
pytest --cov=kvittomall --cov-report=term-missing           # same, with a per-file coverage breakdown
```

There is no linter/formatter configured in this repo - don't invent a command for one. `python3 -m py_compile kvittomall/*.py kvittomall/web/*.py` is a reasonable ad-hoc sanity check after edits, on top of `pytest`. Tests never touch the real `data/`/`final/`/`logs/`/`config/` directories, nor a real `config/pdf_layout.json`/`config/column_mapping.json` if one happens to exist (e.g. from actually running `kvittomall webui` and using `/config`) - `tests/conftest.py` redirects `paths.LOGS_DIR`, `paths.PDF_LAYOUT_PATH`, `config._COLUMN_MAPPING_PATH`, and their `_LEGACY_*_PATH` counterparts (see the `config/` note under Architecture for why those exist and why they need the same treatment) before any other module gets imported, since all of these are read live by most of the suite (any column-name constant, any PDF-layout call), not just by the tests that exercise those files directly - a stray real file previously meant most of the suite silently broke, not a hypothetical, this genuinely happened once those files existed to be created. `pdf_layout` in particular has to be explicitly imported right there in `conftest.py`, immediately after the `PDF_LAYOUT_PATH` patch, since it does `from kvittomall.paths import PDF_LAYOUT_PATH` at module level - a plain value copied in once, at import time, so importing it any later (even implicitly, from within a test module) would bind the real repo path instead. Individual tests monkeypatch `DB_PATH`/`DOWNLOADS_DIR`/etc. on the *consuming* module the same way when they need a value other than this default (not `kvittomall.paths`, since those are plain values copied in at import time via `from kvittomall.paths import X` - patching the source module after that point doesn't affect an already-imported name). `pytest.ini` sets `pythonpath = .`, without which bare `pytest` (as opposed to `python -m pytest`) can't import `kvittomall` at all - `python -m pytest` adds the CWD to `sys.path` automatically, bare `pytest` doesn't, and CI runs the bare form. GitHub Actions (`.github/workflows/tests.yml`) runs the same compile check + `pytest --cov` on every push/PR.

Coverage is deliberately not exhaustive - roughly 64% of statements overall as of when this was written (`pytest --cov` shows the current, real number; don't trust this one once the code has moved on). Roughly:
- **Fully/near-fully covered**: `paths.py`, `pdf_layout.py`, `rowkey.py`, `config.py`, `atomic.py`, `lock.py`, `logging_setup.py` (100%), `db.py` (~96%), `pdf_gen.py` (~95% - both the pure rendering functions and the full `run()` orchestration: new/stale/repair classification, handled-marking/toggling, attachment-readiness gating, `remove_final()`, the unmapped-column warning, and a custom `pdf_layout` actually changing rendered output, all exercised against a real temp DB + real temp `FINAL_DIR`, not mocked), `google_api.py`'s mode/error handling (~84%).
- **Partially covered**: `media.py` (~76% - the adaptive-compression logic and `_process_all`'s `only=` filtering/`remove_processed()` are tested; some adopt-existing/error branches aren't), `sheet.py` (~66% - the pure parsing/validation helpers and the public-fetch/fallback paths are tested; `_fetch_api`'s actual Google API call isn't), `progress.py` (~64% - exercised incidentally via `pdf_gen.run()`'s real `ProgressBar` usage, but not `isatty`-gated rendering itself), `status.py` (~55% - `row_status()`'s classification branches are tested directly in `tests/test_status.py`, including the "PDF removed" vs. "needs repair" distinction; `run()`'s own CLI print-table formatting isn't), `drive.py` (~48% - the pure link-parsing/confirm-token helpers, `_download_all`'s `only=` filtering, and `remove_downloads()` are tested; the actual Drive API/public-download HTTP calls aren't).
- **Untested (0%)**: `cli.py`, `web/app.py`, `__main__.py`. `web/app.py` was verified during development with one-off scratch scripts exercising a Flask test client (not committed as permanent tests) rather than `tests/`-suite coverage - same gap as `cli.py`'s subprocess-level dispatch, just newer.

None of this was arbitrary - it's "pure logic and fail-safe checks first," not "whatever was easiest." Extending coverage into the untested modules is reasonable future work, not a sign something was missed by accident.

System dependency: `libmagic` (`sudo apt-get install libmagic-dev` on Debian/Ubuntu/WSL, `brew install libmagic` on macOS) - `python-magic` needs it to detect file types since Drive downloads don't preserve extensions.

Requires Python 3.10+ (the codebase uses `X | None` union-type syntax throughout).

## Architecture

Single package (`kvittomall/`), one module per pipeline stage plus shared infrastructure. `kvittomall/cli.py` is the only entry point (`python -m kvittomall <command>`); each stage is also a plain function (`sheet.run()`, `drive.run()`, `media.run()`, `pdf_gen.run()`) that can be called directly.

**The state store is the load-bearing piece.** `kvittomall/db.py` holds a SQLite database (`data/kvittomall_state.db`, gitignored) with two tables: `rows` (one row per sheet submission, keyed by its raw `Tidstämpel` timestamp - the one genuinely stable identifier, since a submitter's name can be corrected later) and `attachments` (one row per receipt link within a submission). Every stage treats "is this done?" as a **fail-safe check, never a trusted flag**: a row/attachment only counts as done when the DB says so *and* the recorded file still exists on disk with the expected size *and* a content hash confirms the source sheet row hasn't changed since. Any mismatch resets that item to pending and gets logged with the specific reason - see `db.classify_generated()` and `db.is_download_valid()`/`is_process_valid()`. This is why re-running any stage after an interruption, a deleted file, or an edited sheet row is always safe and never redoes more than necessary.

**Sheet/Drive access has two interchangeable backends.** `kvittomall/google_api.py` holds everything shared between them: `get_access_mode()` reads `ACCESS_MODE` from `.env` (`"api"`, `"public"`, or unset/`"auto"`), and `describe()` turns a raw Google/network exception into a plain-language reason (contextualized by which method hit it, since the same HTTP status means something different on each). `sheet.py` and `drive.py` each implement both a service-account API path and the original anonymous-link path, and pick between them the same way: `"public"`/`"api"` use only that method (the latter raising outright if it fails), `"auto"` tries the API and falls back to the public method with a logged `WARNING` if it fails. `drive.py` decides this once per `download` run (one cheap API call), not per file, since a broken key/share affects every file identically.

**Service account key management is an organizational policy, not a code concern** - the full walkthrough (where to find/create/revoke keys in Google Cloud Console) and the tradeoffs between per-person/per-form/shared keys live in README.md's Konfiguration section, not here. This project's chosen convention: one shared JSON key across everyone who needs it, even across multiple Google Forms, revoked and replaced at the end of each term rather than managed per-person - a deliberate security/convenience tradeoff for a small student committee, not an oversight. If asked to help with onboarding or key rotation, follow that policy rather than suggesting per-person keys unless the user asks to change the approach.

**`kvittomall run` keeps going after a stage fails.** `cli.py`'s `_run_pipeline_stages()` runs all four stages regardless of earlier failures - e.g. a `fetch` that can't reach Google shouldn't stop `generate` from rebuilding a PDF whose data was already downloaded and processed in an earlier run. This only catches `SystemExit`, the deliberate signal every stage uses to end itself (always logged via that stage's own logger first); an unexpected exception is a real bug and is left to propagate. Failed stages are reported together at the end, with a nonzero exit code.

The same "only catch what's expected" discipline applies one level deeper inside `download`: `drive.py`'s `_download_one()` only catches the exception types that mean "this specific attachment failed to download for a describable, Google-side reason" (`HttpError`, `GoogleAuthError`, the public path's `requests` errors, and the module's own deliberate `ValueError`s for known failure modes). A bare `OSError` - e.g. the local disk filling up while writing into `downloads/` - is deliberately left uncaught there, so it propagates and crashes the `download` stage outright instead of being recorded as one more failed attachment and silently retried, unexplained, on every future run.

**Writes are atomic.** `kvittomall/atomic.py`'s `atomic_write()` writes to a temp file in the same directory, validates it (page count, image integrity, MIME type depending on stage), then `os.replace()`s it into place - only after that does the DB get updated. A process killed mid-write never leaves a half-written file mistaken for a finished one.

**`final/` output layout is intentional, not incidental.** `final/<category>/` (`privat/`, `sektionskort/`, `milersättning/`, `övrigt/` - see `config.category_for()`, keyed off the sheet's `Transaktionstyp` column) is cumulative, not a "latest batch" folder - it holds every generated PDF that hasn't been reviewed yet, and nothing moves out of it automatically. Review is a deliberate, per-entry (or bulk) human action: `kvittomall handled [row_key]` moves a row's PDF into `final/handled/<category>/`. Whether a row is handled is its own `handled` boolean column in `db.py` - deliberately *not* folded into `status` (which stays `"new"`/`"generated"`/`"error"` throughout, so `db.classify_generated()` never needs to know or care about review state - a handled row's `status` is still just `"generated"`). Running `kvittomall handled <row_key>` a second time on an already-handled row **toggles it back** (`pdf_gen.toggle_handled()`) - handled and unhandled are symmetric, both just "move the file, flip the column" (`pdf_gen._move_between()`). The bulk form (`kvittomall handled` with no row key, and the dashboard's "Mark all handled" button, both `pdf_gen.mark_all_handled()`) is deliberately **not** a toggle - it only ever advances not-yet-handled rows to handled, never the reverse, since toggling a mixed batch in one pass has no useful/predictable meaning. If a handled row's sheet content later changes, `db.classify_generated()` reclassifies it as stale purely on the content-hash mismatch (independent of the `handled` column), and `pdf_gen.run()` writes the regenerated PDF back into the active category folder, explicitly resetting `handled` to `False` as part of the same `db.mark_generated()` call - review state is always set explicitly on every generation, never left as whatever it happened to be before, so a stale regeneration can never silently stay "handled" while sitting in the wrong folder. A row whose content is unchanged but whose file went missing (accidental deletion) is treated as a repair and restored to wherever it already was (category folder or `handled/`, preserving its current `handled` value), not surfaced as new - see the `"repair"` vs `"stale"` distinction in `db.classify_generated()` and how `pdf_gen.run()` branches on it. (This replaced an earlier automatic-sweep mechanism that archived a category's entire folder into `final/previous/<category>/` whenever any row in it needed regenerating - removed once per-entry review made a deliberate, human-driven mark more useful than an automatic one. A `handled` *status* value briefly stood in for the boolean column before this - `db.connect()`'s `_migrate()` upgrades any row still carrying it.)

**Removing files is deliberately separate from removing data.** `kvittomall remove <row_key> [--only downloads|processed|final]` deletes an entry's on-disk file(s) - never the CSV, the DB row, or the entries list - and, unlike every other scoped command, always requires a row key (no bulk "wipe everything" mode). It needs no new fail-safe logic of its own: `drive.remove_downloads()`/`media.remove_processed()`/`pdf_gen.remove_final()` just delete the file and leave the DB exactly as it was, because `is_download_valid()`/`is_process_valid()`/`classify_generated()` already re-verify a file's presence on disk before ever trusting a recorded path - a later `download`/`process`/`generate` treats a manually-removed file exactly like any other accidental deletion and simply redoes that one piece of work.

**A CLI/web action can be scoped to one entry.** `download`, `process`, `generate`, `handled`, and `run` all accept an optional row_key (the row's stable `Tidstämpel`-based identity from `rowkey.row_key()`, *not* its CSV position, which isn't stable across re-fetches) to act on a single row instead of every row - see `cli.py`'s `SCOPABLE_STAGES` and each stage module's `run(only=...)` parameter. `fetch` is the one exception (it always pulls the whole sheet). A scoped `run <row_key>` skips `fetch` entirely. `remove` is scoped by design but intentionally left out of `SCOPABLE_STAGES`/`STAGES` (it takes an extra `--only` axis those don't). `receipt_links(row)` in `rowkey.py` (parses the raw comma-separated links column) is shared by `drive.py`, `pdf_gen.py`, and `status.py` so "how many attachments should this row have" is computed identically everywhere, straight from the CSV - not from however many attachment rows happen to exist in the DB already, which would under-report a row that has links but hasn't been downloaded yet.

**The local web UI (`kvittomall webui`, `kvittomall/web/app.py`) is a thin control panel over these same functions**, not a second implementation of any pipeline logic - every stage/remove button ultimately calls the same `STAGES`/`REMOVE_TARGETS` callables `cli.py` does (the one exception is "Clean all," which calls `paths.clean_all()` directly - see below), background-threaded (`threading.Thread` + a single global `_running` slot) so a request returns immediately, and still serialized through the same `run_lock()` every CLI invocation uses (so the web UI and a concurrent terminal command can never mutate state at once). It binds `0.0.0.0` by default (`config.WEBUI_HOST`/`WEBUI_PORT`, overridable via `.env`) rather than `127.0.0.1`, deliberately - the machine this typically runs on (a home server/VM) is rarely the machine you browse from - which also means there's no authentication on any route; that's a real tradeoff, not an oversight, and worth surfacing rather than "fixing" unprompted. The dashboard (`/`) carries the whole-pipeline buttons *and* the full entries list in one page - not a separate `/entries` route - so triggering an action and having the list itself update are on the same page; every dashboard action polls `/api/status` until it finishes and then does a full `location.reload()`, since the entries table is rendered server-side and has no other way to pick up new state (`entry_detail.html` does the same after a per-row action). `/entries/<row_key>` is still its own page for one row's detail (attachments, the final PDF, every other non-empty CSV field, and the same scoped-action buttons).

**The entries list is sortable and filterable entirely client-side** (`index.html`'s second `<script>` block) - no query params, no server round-trip, since the data is already fully present in the rendered `<table>` and this tool's data volume never justifies more. Clicking a header sorts by that column (numeric-aware: it tries parsing both sides as a number, handling the Swedish decimal comma, before falling back to text comparison); a filter input under each header narrows independently, combined with AND across columns. Its curated columns (Date/Sum/Committee/Event/Specification, Category and Name pinned first) are pulled through `config.py`'s column constants via `web/app.py`'s `ENTRIES_LIST_COLUMNS` - never a hardcoded sheet header - and "Sum" is really a list of columns tried in order (`SUM_COLUMN`, falling back to `MIL_COLUMN`), since a `Milersättning` row has no `Summa` of its own. Numeric-looking values (there and in the detail page's generic field list) are passed through `_swedish_decimal()`, which only touches a value that's unambiguously a plain dotted decimal (`^-?\d+\.\d+$`) - safe to apply to arbitrary CSV text without risking something like an account number or URL that just happens to contain a dot.

**The entry detail page never trusts a DB path without checking disk, and says so plainly.** `status.row_status()` computes `final_pdf_exists` with its own direct `os.path.exists()` check, separate from `final_pdf_path` (which is just the DB's recorded location and stays set even after the file is deleted, by design - see the `remove` command above) - the template shows a link only when `final_pdf_exists` is true, otherwise the same plain "not generated"/"not downloaded"/"not processed" wording used for attachments, instead of a stale-looking link to a 404. When `classify_generated()` returns `"repair"` specifically because the file is missing (as opposed to zero-byte or wrong-size, which mean it's still physically there but corrupt), `row_status()` shows a short "PDF removed" instead of `classify_generated()`'s diagnostic reason string, which embeds a full filesystem path - not something to put in front of a user. Downloaded/processed attachments render as an `<img>` thumbnail (wrapped in a link to the full file) when the extension is one a browser can actually display inline (`DOWNLOAD_IMAGE_EXTENSIONS`/`PROCESSED_IMAGE_EXTENSIONS` in `web/app.py`) - HEIC/HEIF, a realistic raw-download format for a phone photo before `process` converts it to JPEG, deliberately stays a plain link instead, since browsers generally can't render it and a broken-image thumbnail would be worse than no thumbnail.

**A destructive action gets a destructive-looking button.** The dashboard's "Clean all" (red, its own "danger zone" section, gated by a `confirm()` popup spelling out exactly what it does) calls `paths.clean_all()`: `shutil.rmtree()` on `DATA_DIR` and `FINAL_DIR` specifically (nothing else - `ROOT`/`DATA_DIR`/`FINAL_DIR` are assigned exactly once in `paths.py` and never reassigned anywhere else in the codebase), then `ensure_dirs()` to recreate the empty layout - the same state as a machine that's never run the pipeline. `logs/` is deliberately untouched (audit trail, not pipeline state). It's web-only by design, not exposed as a CLI command - the bar for "one click, no typing" should be higher for something this irreversible than for the rest of the UI.

**PDF cover-page content is config-driven, and now web-editable on top of that.** `kvittomall/config.py`'s `default_pdf_sections()` (a function returning a list of `Section`/`Field` dataclasses, built from the current column mapping - see below) is still the compiled-in *default* layout - each `Field` maps a label to a sheet column and an optional value formatter (`currency()`/`mil()`, which append the unit *and* normalize the decimal separator to a comma; `str` for plain text). A `Field` with an empty label renders full-width with no bold prefix, for content that shouldn't look like a label/value pair - currently unused, but supported. What `pdf_gen.py` actually renders, though, is `pdf_layout.get_pdf_sections()` - `kvittomall/pdf_layout.py` reads a small JSON file (`paths.PDF_LAYOUT_PATH`, under `paths.CONFIG_DIR` - deliberately outside `DATA_DIR`/`FINAL_DIR` so `clean_all()` never touches it, and in its own directory rather than directly at the repo root for a Docker-specific reason explained further down) if one exists, falling back to `config.default_pdf_sections()` if not. The web UI's `/config` page (its "PDF cover page layout" section) edits that file directly (client-side, as one JSON blob via `fetch()` to `/pdf-layout` - not a nested HTML form, which Flask can't parse natively anyway) letting a user remap which column feeds each field, add/remove/reorder fields and sections, and pick a formatter, all without touching code. A legend at the top of that section spells out what each control does (the label text box, the column dropdown, the format dropdown), since none of it is self-explanatory to someone seeing it for the first time. The format dropdown's stored values are still `pdf_layout.FORMATTERS`'s keys (`"plain"`/`"currency"`/`"mil"`, unchanged - what's actually in the JSON and what `pdf_gen.py` looks up), but it displays as "None"/"kr"/"mil" - what the choice actually *does* (append no suffix, "kr", or "mil"), not the internal formatter name. Each field's dropdown offers one option per named `SHEET_COLUMN_*` setting (`config.column_settings()`), not an arbitrary raw CSV column - labeled `"{label}: {current value}"` (e.g. "Sum: Summa") so the physical column behind each choice is always visible, and flagged right on the option if that setting's current value isn't in the last-fetched sheet at all. A genuinely unnamed sheet column (e.g. `Godkännande`, a self-attestation checkbox with no constant at all) was previously selectable here like any other - now it isn't; give it a name via a `SHEET_COLUMN_*` setting first if it should ever appear on the cover page. `TIMESTAMP_COLUMN`, `RECEIPT_LINKS_COLUMN`, and `TRANSACTION_TYPE_COLUMN` are deliberately never offered as a mapping target here (`pdf_layout.non_display_columns()`, enforced both by the UI's dropdown options and server-side in `web/app.py`'s `_validate_pdf_layout()`) - they determine row identity, attachment discovery, and the category folder respectively, not just what's printed on the page, so letting a web form repoint them risks corrupting existing state. `NAME_COLUMN` is structural too (it drives `rowkey.base_filename()`) but, unlike those three, is also a perfectly ordinary thing to display - the default layout's own "Namn:" field maps straight to it - so it's deliberately *not* in `non_display_columns()`, only in the broader `pdf_layout.structural_columns()` (used for `known_columns()` below, not for this exclusion). Getting this distinction wrong once meant the dropdown's column pool and `_validate_pdf_layout()` both used the broader set, which filtered "Namn" out of the dropdown and then rejected saving the default layout outright - a real bug, not a hypothetical one, fixed by splitting the two sets. A field whose saved column doesn't match any current choice (e.g. a legacy freeform pick from before this restriction existed) is kept as its own flagged option rather than silently dropped or changed. The layout is read fresh on every `generate` (not cached), so a web-UI edit takes effect immediately, from either the CLI or the web UI, without restarting `kvittomall webui`.

**A CSV column with data but no home gets flagged, per PDF, not globally - and right on the field itself, not as a page-wide banner.** `pdf_layout.unmapped_columns_with_data(row)` compares a row's non-empty columns against `pdf_layout.known_columns()` (every column the current layout maps, plus `pdf_layout.structural_columns()`) and returns whatever's left over - `pdf_gen.run()` logs a `WARNING` for each row it actually (re)generates that has any, and `status.row_status()` computes the same thing for `entry_detail.html`, independent of whether a generation just happened. The detail page renders every non-empty field in a plain list (`info.fields`), and appends a small `⚠` next to just the field(s) whose column is in `info.unmapped_columns` - a native `title` tooltip on that icon carries the explanation (won't appear on the generated PDF, fix via Configuration → PDF layout), so the warning sits beside the specific data it's about instead of a separate banner naming columns the reader then has to go find. Crucially this is evaluated **per row**, not as a fixed set of "always missing" columns: a mapped-but-currently-empty field (e.g. `MIL_COLUMN` on an ordinary, non-mileage expense) is never flagged - it's normal for it to be blank on most rows - only a column that's both unmapped *and* has an actual value on *this* row triggers the warning, and it's a warning, never something that blocks generation.

**The header logo can be SVG or a raster image, and the difference in output size is not subtle.** `config.LOGO` names the file (in the repo root, resolved to `paths.LOGO_PATH`); `pdf_gen._draw_page_header()` - called on *every* page, cover and attachments alike - checks the extension and renders it one of two ways. A `.svg` goes through `svglib`'s `svg2rlg()` (cached via `@lru_cache`, since re-parsing the file from disk on every page would be wasteful) and `reportlab.graphics.renderPDF`; anything else goes through the original `ImageReader`/`drawImage` path. This isn't a style choice: ReportLab embeds a raster image inefficiently (raw pixels through `FlateDecode` *and* `ASCII85Decode`, with no de-duplication across the separately-built pages that later get merged via pypdf), so the same logo redrawn on every page can multiply a receipt's file size several times over - a true vector SVG (not one that just wraps a raster image internally) avoids nearly all of that. Swapping the logo is just changing `config.LOGO` to a filename that exists in the repo root; nothing else needs to change.

**Image compression is a legibility-vs-size tradeoff, not baked in.** `config.IMAGE_QUALITY` names which tier is active - `"normal"` by default, overridable via `IMAGE_QUALITY` in `.env` through the same `_env()` pattern as the sheet columns. `media.py`'s `QUALITY_PRESETS` defines what each of the five names (`extreme`, `high`, `normal`, `low`, `potato`) actually means: a `QualityPreset(max_dimension, quality_steps, target_bytes, hard_ceiling, dimension_rounds)` - `encode_adaptive()` starts at the preset's highest quality step and only steps down (then shrinks dimensions, if still over `hard_ceiling`) as far as needed to fit `target_bytes`. `extreme` has `target_bytes=None`, so it always returns after a single high-quality pass with no resize - the point is legibility, not a polished photo, so even `normal` compresses harder than a typical image pipeline would. `media.py`'s `get_quality_preset()` is the one that validates `config.IMAGE_QUALITY` against the actual preset names (config.py just holds the configured string, since it doesn't know what's valid), raising `SystemExit` on an unrecognized value - resolved once per `process` run via the same "fail fast before doing any work" pattern as `drive.py`'s `_get_drive_service()`. Changing the setting only affects attachments processed *after* the change - already-processed files in `data/processed/` stay valid per the fail-safe checks above and aren't retroactively redone.

**Every sheet column name is configurable, not hardcoded - and, since a mismatched default is now web-fixable, this has a third layer, resolved live.** `config.py` defines one dynamic attribute per column the pipeline actually reads (`TIMESTAMP_COLUMN`, `NAME_COLUMN`, `SUM_COLUMN`, `MIL_COLUMN`, `ROUTE_COLUMN`, etc.), each resolved by `_column(env_var, default)` in this order: `column_mapping.json` (the web UI's `/config` page, "Sheet column mapping" section), then the matching `SHEET_COLUMN_*` variable in `.env`, then the compiled-in default (the current Google Form's exact wording). `config.py` calls `load_dotenv()` at import time (not inside any one stage's `run()`), so this - and every other `.env`-driven setting read anywhere in the codebase - is guaranteed loaded regardless of which single stage gets invoked standalone; `column_mapping.json` is read the same way, at the same time, for the same reason. `_column()` is deliberately distinct from the plain `_env()` used for non-column settings (`IMAGE_QUALITY`, `WEBUI_HOST`) - only the sheet-column constants get the override-file layer. `_ROOT`/`_COLUMN_MAPPING_PATH` are computed independently in `config.py` rather than imported from `paths.py` - `paths.py` already does `from kvittomall.config import LOGO` at module level, so the reverse import would be circular (would fail with a partially-initialized-module error, not just a lint warning - this was verified, not assumed). Unlike a plain `.env` change, **a `column_mapping.json` change takes effect immediately, on the very next access, with no restart of `kvittomall webui` or any CLI command needed** - these aren't plain module-level constants anymore but PEP 562 dynamic attributes: `config.py`'s module-level `__getattr__(name)` resolves any name in `_COLUMN_DEFAULTS` (e.g. `TIMESTAMP_COLUMN`) fresh on every `config.X_COLUMN` attribute access, the same live-reload pattern `pdf_layout.get_pdf_sections()` already used for the PDF layout. This only works because every consumer (`rowkey.py`, `sheet.py`, `status.py`, `pdf_gen.py`, `web/app.py`) accesses these as `config.X_COLUMN` via `from kvittomall import config`, never as `from kvittomall.config import X_COLUMN` - the latter would evaluate once at that import statement and cache a stale snapshot in the importing module's own namespace, silently defeating the whole mechanism. `column_settings()` and `default_pdf_sections()` are functions for the same reason, replacing what used to be static `COLUMN_SETTINGS`/`PDF_SECTIONS` lists. Only columns the pipeline structurally depends on get a constant; a column that exists in the sheet purely for the submitter's own record (e.g. `Godkännande`, a self-attestation checkbox) has no constant, is never treated as row identity/attachments/category, and never appears on a generated PDF unless someone explicitly maps it via `/pdf-layout` - though `pdf_layout.unmapped_columns_with_data()` will still (correctly) flag it as unmapped-with-data if it's ever filled in, which is a deliberate visibility feature, not a bug to "fix" by giving it a constant. See `category_for()`'s docstring note distinguishing a column's header (has a constant) from the *values* inside it (matched literally in `CATEGORY_MAP`, which doesn't need one).

**The "Sheet column mapping" section exists because the PDF layout section's column dropdown can't tell you which of two similar-looking strings is real - which is also why the two sections live on the same `/config` page rather than two separate ones.** If a deployment's actual Google Form wording doesn't match a `SHEET_COLUMN_*` default (nobody's fixed `.env`), the PDF layout dropdown used to union "columns in the last fetch" with "columns the current layout references" - so a genuinely dead reference (the wrong default) and the real column both appeared as normal-looking, indistinguishable dropdown options. That dropdown now offers **only** columns actually discovered in the last-fetched CSV; a field whose current mapping isn't among them is kept as its own option (so saving without touching that field never silently changes it) but visibly marked "not found in last fetch" instead of looking like a normal choice. The column mapping section is the actual fix for *why* it's not found: for all 13 `SHEET_COLUMN_*` settings (`config.column_mapping_rows()`, built on top of the same `_COLUMN_DEFAULTS` dict `config.column_settings()` uses, but also exposing `overridden`/`default_value` per setting for this section specifically), it shows the current resolved value, flags it the same way if it's not among the discovered columns, and - since the whole point is "the user must configure this themselves, it can't be done automatically" - shows a live sample value from the first fetched row next to each dropdown choice, so a mapping can be visually confirmed before saving instead of guessed at. Every dropdown's first option is **"(Default)"** - selecting it sends an empty string for that setting, which `save_column_mapping()` drops before writing `column_mapping.json` (`if value.strip()`), leaving that `SHEET_COLUMN_*` to keep resolving via `.env`/the compiled default rather than being pinned to a specific column - the right choice for a column that's genuinely absent from a given deployment's sheet (e.g. `MIL_COLUMN` for a committee that never reimburses mileage), where every other option would otherwise force an incorrect explicit mapping. The four structural columns are shown in their own subsection with an explicit, undismissable warning: remapping one after rows have already synced under the old mapping orphans their identity on the next fetch (existing downloads/processed files/PDFs aren't deleted, just no longer linked to anything) - the same risk `.env`-editing always had, just finally visible instead of a silent trap.

**Saving `/column-mapping` also migrates any already-saved PDF layout off the columns it just changed.** `pdf_layout.json` stores each field's column as a plain resolved string (e.g. `"Datum för händelsen"`), not a live reference back to `config.DATE_COLUMN` - `default_sections_data()` re-resolves live every time precisely because it's *never* persisted, but the moment a layout is saved even once (including just to reorder something, touching no field), every field's column freezes to whatever it resolved to at that instant. Without help, fixing a wrong `SHEET_COLUMN_*` mapping afterward would leave an already-saved field silently pointing at the old, now-wrong column forever. `web/app.py`'s `save_column_mapping()` handles this itself: it snapshots every setting's resolved value (`config.column_settings()`) both before and after applying the new overrides, builds an `{old value: new value}` dict for whatever actually changed, and passes it to `pdf_layout.migrate_columns()`, which rewrites any field whose column is an exact key in that dict - and leaves everything else untouched, since a field pointing at some freeform column never tracked a `SHEET_COLUMN_*` setting to begin with. A no-op, no-write case (layout never customized, or nothing in it matches) is exactly as cheap as it sounds.

**Logging**: `kvittomall/logging_setup.py` gives every stage a logger writing to `logs/{stage}-{year}-{month}.log` (Swedish/`Europe/Stockholm` timestamps regardless of host timezone, monthly files so they don't grow forever). Console output is WARNING-and-above by design - routine progress is a live progress bar (`kvittomall/progress.py`), coordinated with the logging handler so a warning/error print doesn't get mangled mid-bar.

**`data/` (downloads/, processed/, responses.csv, kvittomall_state.db, the lock file), plus `final/`, `logs/`, `.env`, and any `*.json` (service account key), are all gitignored runtime state - none of it is precious.** `data/` holds everything the pipeline owns and rebuilds itself (see `paths.py`); it's kept separate from `final/` (the actual deliverable output) and `logs/` (kept easy to check without digging in), both of which stay in the repo root. The Google Sheet is the source of truth; any of this can be deleted and rebuilt with `python -m kvittomall run` (existing valid downloads/processed files get adopted rather than redone, per the fail-safe checks above) - `paths.clean_all()` (the web UI's "Clean all" button) is this same idea taken deliberately, doing the deleting for you instead of waiting for it to happen by accident.

**Docker is an alternative way to run this, not a second implementation.** `Dockerfile` builds a `python:3.12-slim` image (`apt-get install libmagic1` for `python-magic`, then `pip install -r requirements.txt`, then `COPY . .`) with `ENTRYPOINT ["python", "-m", "kvittomall"]` and `CMD ["webui"]`, so `docker run <image> fetch` (or any other subcommand) works exactly like the CLI does, and the bare image just starts the web UI. `.dockerignore` mirrors `.gitignore` (plus `.git/`, `venv/`, `tests/`, dev-only files) - the same gitignored runtime state above, including every `*.json`, never gets baked into the image; it's supplied at `docker run`/`docker compose up` time as bind mounts instead. Since `paths.ROOT` is computed from `kvittomall/paths.py`'s own `__file__` location, and the Dockerfile does `WORKDIR /app` + copies the package to `/app/kvittomall/`, every path this project resolves relative to the repo root (`data/`, `final/`, `logs/`, `config/`, `config.LOGO`) resolves to `/app/<name>` inside the container - `docker-compose.yml`'s volumes target exactly those paths, nothing computed differently for Docker specifically. The container runs as root, deliberately, the same "simplicity over hardening" tradeoff as the web UI's lack of authentication (see below) - the alternative (a non-root user) routinely hits bind-mount permission mismatches on first run, which would work against the entire point of Docker being the *easier* setup path. The concrete cost, verified by actually running it: files created under `data/`/`final/`/`logs/` land on the host owned by root, not whichever user ran `docker compose up` - worth knowing before being surprised by a permission-denied trying to inspect or delete them directly from the host.

**`config/` (holding `pdf_layout.json`/`column_mapping.json`) exists as its own directory specifically because of a real bug Docker exposed, not by original design.** These two started out living directly at the repo root (like `.env`/the logo), which worked fine for CLI/venv use - but bind-mounting either file individually for Docker persistence made every `/config` save fail outright with `OSError: [Errno 16] Device or resource busy`, and a symlink-based workaround silently wrote to the wrong place instead (both verified by actually running them, not assumed): `atomic_write()`'s write-temp-then-`os.replace()` pattern can't rename onto a path the container runtime has bind-mounted as a single file - the kernel refuses it - and `os.replace()` onto a symlink replaces the symlink itself rather than following it. Moving both files into `paths.CONFIG_DIR` (a directory `ensure_dirs()` now also creates, alongside `DATA_DIR`/`FINAL_DIR`/`LOGS_DIR`) fixes this because renaming a file *within* a mounted directory is a completely ordinary operation - only the mount point itself is special. `pdf_layout.py`/`config.py` each carry a small one-time, silent migration (`_migrate_legacy_file()`/`_migrate_legacy_override_file()`) for anyone who already has a file at the old repo-root location, run from the read path (`load_sections_data()`/`_column_overrides()`) before checking the current path - never overwrites a file already at the new location. `tests/conftest.py` redirects the two `_LEGACY_*_PATH` module attributes the same way it redirects everything else path-related, and for the same reason: both are computed from `paths.ROOT`/`config._ROOT`, real unmocked constants no test ever overrides, so left alone a test would risk silently *moving* an actual repo-root file into a throwaway temp directory the first time it read a layout or column setting.

## Module map

| Module | Responsibility |
|---|---|
| `paths.py` | All path constants (incl. `CONFIG_DIR`), `ensure_dirs()`, `clean_all()` (wipes `data/`+`final/` back to an empty layout, never `config/`) |
| `config.py` | Sheet column names (overridable via `.env` or `/column-mapping`'s `column_mapping.json`, both live-reloaded via `__getattr__`), `column_settings()`, the compiled-in default `default_pdf_sections()`, category mapping, `load_dotenv()` |
| `pdf_layout.py` | The *actual* (possibly web-UI-edited) PDF cover-page layout - `get_pdf_sections()`, `save_sections_data()`, `unmapped_columns_with_data()`, `migrate_columns()` |
| `rowkey.py` | Row identity, filename sanitization, content/link hashing, `receipt_links()`, DB sync (incl. renaming files in place if a submitter's name changes) |
| `db.py` | Schema + all state read/write, including the fail-safe validity checks |
| `atomic.py` | `atomic_write()` |
| `lock.py` | Single-instance file lock for mutating commands |
| `google_api.py` | `ACCESS_MODE` handling, service-account credential/service builders, error-message translation - shared by `sheet.py` and `drive.py` |
| `sheet.py` | Stage 1 (fetch/validate CSV, via API or public export) + `read_rows()`, used by every later stage |
| `drive.py` | Stage 2 (download, via API or public link), per-attachment state, adopts pre-existing downloads, `remove_downloads()` |
| `media.py` | Stage 3 (adaptive JPEG compression via `IMAGE_QUALITY` presets / PDF passthrough), adopts pre-existing processed files, `remove_processed()` |
| `pdf_gen.py` | Stage 4 (cover page + attachment merge, via `pdf_layout.get_pdf_sections()`) plus the `handled` review workflow (`toggle_handled`/`mark_all_handled`/`run_handled`) and `remove_final` |
| `status.py` | Read-only status report + `row_status()`, the fail-safe per-row classification (incl. `final_pdf_exists`, `unmapped_columns`) shared with the web UI |
| `cli.py` / `__main__.py` | Argument parsing and dispatch, incl. `REMOVE_TARGETS`/`remove_all_files()` reused by the web UI |
| `web/app.py` | Local web UI (`kvittomall webui`) - dashboard (`/`) embeds the sortable/filterable entries list and the "Clean all" reset button; `/entries/<row_key>` is the per-row detail page; `/config` (one page, two sections) edits the cover-page field mapping/order and the `SHEET_COLUMN_*` name-to-header mapping, saved via `/pdf-layout` and `/column-mapping` respectively |
