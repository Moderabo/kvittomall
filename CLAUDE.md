# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Automates creating expense-receipt PDF reports ("kvittomallar") for a student committee. Pulls submissions from a Google Sheet (backed by a Google Form), downloads the linked receipt images/PDFs from Google Drive, and generates one combined PDF per submission (cover page + attachments).

## Commands

```sh
python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt        # versions are pinned intentionally - keep them pinned

python -m kvittomall run               # fetch -> download -> process -> generate, in order
python -m kvittomall fetch             # Sheet -> data/responses.csv
python -m kvittomall download          # Drive links in data/responses.csv -> data/downloads/
python -m kvittomall process           # data/downloads/ -> data/processed/ (adaptive JPEG compression)
python -m kvittomall generate          # data/processed/ + data/responses.csv -> final/<category>/
python -m kvittomall status            # read-only report of per-row/attachment state, no lock taken
```

```sh
pip install -r requirements-dev.txt                       # adds pytest + pytest-cov on top of requirements.txt
pytest                                                      # run the test suite (tests/, config in pytest.ini)
pytest --cov=kvittomall --cov-report=term-missing           # same, with a per-file coverage breakdown
```

There is no linter/formatter configured in this repo - don't invent a command for one. `python3 -m py_compile kvittomall/*.py` is a reasonable ad-hoc sanity check after edits, on top of `pytest`. Tests never touch the real `data/`/`final/`/`logs/` directories - `tests/conftest.py` redirects `paths.LOGS_DIR` before any stage module gets imported, and individual tests monkeypatch `DB_PATH`/`DOWNLOADS_DIR`/etc. on the *consuming* module (not `kvittomall.paths`, since those are plain values copied in at import time via `from kvittomall.paths import X` - patching the source module after that point doesn't affect an already-imported name). `pytest.ini` sets `pythonpath = .`, without which bare `pytest` (as opposed to `python -m pytest`) can't import `kvittomall` at all - `python -m pytest` adds the CWD to `sys.path` automatically, bare `pytest` doesn't, and CI runs the bare form. GitHub Actions (`.github/workflows/tests.yml`) runs the same compile check + `pytest --cov` on every push/PR.

Coverage is deliberately not exhaustive - roughly 68% of statements overall as of when this was written (`pytest --cov` shows the current, real number; don't trust this one once the code has moved on). Roughly:
- **Fully/near-fully covered**: `rowkey.py`, `config.py`, `atomic.py`, `lock.py` (100%), `pdf_gen.py` (97% - both the pure rendering functions and the full `run()` orchestration: new/stale/repair classification, handled-marking, attachment-readiness gating, all exercised against a real temp DB + real temp `FINAL_DIR`, not mocked), `db.py`, `logging_setup.py` (~95%), `google_api.py`'s mode/error handling (~84%).
- **Partially covered**: `sheet.py` (~66% - the pure parsing/validation helpers and the public-fetch/fallback paths are tested; `_fetch_api`'s actual Google API call isn't), `progress.py` (~59% - exercised incidentally via `pdf_gen.run()`'s real `ProgressBar` usage, but not `isatty`-gated rendering itself), `media.py`/`drive.py` (30-44% - the pure compression/parsing logic is tested, the per-attachment download/process orchestration isn't yet, unlike `pdf_gen.py`'s equivalent which now is).
- **Untested (0%)**: `cli.py`, `status.py`, `__main__.py`. Would need either subprocess-level tests or heavy mocking of every stage - not done yet.

None of this was arbitrary - it's "pure logic and fail-safe checks first," not "whatever was easiest." Extending coverage into the untested modules is reasonable future work, not a sign something was missed by accident.

System dependency: `libmagic` (`sudo apt-get install libmagic-dev` on Debian/Ubuntu/WSL, `brew install libmagic` on macOS) - `python-magic` needs it to detect file types since Drive downloads don't preserve extensions.

Requires Python 3.10+ (the codebase uses `X | None` union-type syntax throughout).

## Architecture

Single package (`kvittomall/`), one module per pipeline stage plus shared infrastructure. `kvittomall/cli.py` is the only entry point (`python -m kvittomall <command>`); each stage is also a plain function (`sheet.run()`, `drive.run()`, `media.run()`, `pdf_gen.run()`) that can be called directly.

**The state store is the load-bearing piece.** `kvittomall/db.py` holds a SQLite database (`data/kvittomall_state.db`, gitignored) with two tables: `rows` (one row per sheet submission, keyed by its raw `Tidstämpel` timestamp - the one genuinely stable identifier, since a submitter's name can be corrected later) and `attachments` (one row per receipt link within a submission). Every stage treats "is this done?" as a **fail-safe check, never a trusted flag**: a row/attachment only counts as done when the DB says so *and* the recorded file still exists on disk with the expected size *and* a content hash confirms the source sheet row hasn't changed since. Any mismatch resets that item to pending and gets logged with the specific reason - see `db.classify_generated()` and `db.is_download_valid()`/`is_process_valid()`. This is why re-running any stage after an interruption, a deleted file, or an edited sheet row is always safe and never redoes more than necessary.

**Sheet/Drive access has two interchangeable backends.** `kvittomall/google_api.py` holds everything shared between them: `get_access_mode()` reads `ACCESS_MODE` from `.env` (`"api"`, `"public"`, or unset/`"auto"`), and `describe()` turns a raw Google/network exception into a plain-language reason (contextualized by which method hit it, since the same HTTP status means something different on each). `sheet.py` and `drive.py` each implement both a service-account API path and the original anonymous-link path, and pick between them the same way: `"public"`/`"api"` use only that method (the latter raising outright if it fails), `"auto"` tries the API and falls back to the public method with a logged `WARNING` if it fails. `drive.py` decides this once per `download` run (one cheap API call), not per file, since a broken key/share affects every file identically.

**Service account key management is an organizational policy, not a code concern** - the full walkthrough (where to find/create/revoke keys in Google Cloud Console) and the tradeoffs between per-person/per-form/shared keys live in README.md's Konfiguration section, not here. This project's chosen convention: one shared JSON key across everyone who needs it, even across multiple Google Forms, revoked and replaced at the end of each term rather than managed per-person - a deliberate security/convenience tradeoff for a small student committee, not an oversight. If asked to help with onboarding or key rotation, follow that policy rather than suggesting per-person keys unless the user asks to change the approach.

**`kvittomall run` keeps going after a stage fails.** `cli.py`'s `_run_pipeline_stages()` runs all four stages regardless of earlier failures - e.g. a `fetch` that can't reach Google shouldn't stop `generate` from rebuilding a PDF whose data was already downloaded and processed in an earlier run. This only catches `SystemExit`, the deliberate signal every stage uses to end itself (always logged via that stage's own logger first); an unexpected exception is a real bug and is left to propagate. Failed stages are reported together at the end, with a nonzero exit code.

The same "only catch what's expected" discipline applies one level deeper inside `download`: `drive.py`'s `_download_one()` only catches the exception types that mean "this specific attachment failed to download for a describable, Google-side reason" (`HttpError`, `GoogleAuthError`, the public path's `requests` errors, and the module's own deliberate `ValueError`s for known failure modes). A bare `OSError` - e.g. the local disk filling up while writing into `downloads/` - is deliberately left uncaught there, so it propagates and crashes the `download` stage outright instead of being recorded as one more failed attachment and silently retried, unexplained, on every future run.

**Writes are atomic.** `kvittomall/atomic.py`'s `atomic_write()` writes to a temp file in the same directory, validates it (page count, image integrity, MIME type depending on stage), then `os.replace()`s it into place - only after that does the DB get updated. A process killed mid-write never leaves a half-written file mistaken for a finished one.

**`final/` output layout is intentional, not incidental.** `final/<category>/` (`privat/`, `sektionskort/`, `milersättning/`, `övrigt/` - see `config.category_for()`, keyed off the sheet's `Transaktionstyp` column) is cumulative, not a "latest batch" folder - it holds every generated PDF that hasn't been reviewed yet, and nothing moves out of it automatically. Review is a deliberate, per-entry (or bulk) human action: `kvittomall handled [row_key]` moves a row's PDF into `final/handled/<category>/`. Whether a row is handled is its own `handled` boolean column in `db.py` - deliberately *not* folded into `status` (which stays `"new"`/`"generated"`/`"error"` throughout, so `db.classify_generated()` never needs to know or care about review state - a handled row's `status` is still just `"generated"`). Running `kvittomall handled <row_key>` a second time on an already-handled row **toggles it back** (`pdf_gen.toggle_handled()`) - handled and unhandled are symmetric, both just "move the file, flip the column" (`pdf_gen._move_between()`). The bulk form (`kvittomall handled` with no row key, and the dashboard's "Mark all handled" button, both `pdf_gen.mark_all_handled()`) is deliberately **not** a toggle - it only ever advances not-yet-handled rows to handled, never the reverse, since toggling a mixed batch in one pass has no useful/predictable meaning. If a handled row's sheet content later changes, `db.classify_generated()` reclassifies it as stale purely on the content-hash mismatch (independent of the `handled` column), and `pdf_gen.run()` writes the regenerated PDF back into the active category folder, explicitly resetting `handled` to `False` as part of the same `db.mark_generated()` call - review state is always set explicitly on every generation, never left as whatever it happened to be before, so a stale regeneration can never silently stay "handled" while sitting in the wrong folder. A row whose content is unchanged but whose file went missing (accidental deletion) is treated as a repair and restored to wherever it already was (category folder or `handled/`, preserving its current `handled` value), not surfaced as new - see the `"repair"` vs `"stale"` distinction in `db.classify_generated()` and how `pdf_gen.run()` branches on it. (This replaced an earlier automatic-sweep mechanism that archived a category's entire folder into `final/previous/<category>/` whenever any row in it needed regenerating - removed once per-entry review made a deliberate, human-driven mark more useful than an automatic one. A `handled` *status* value briefly stood in for the boolean column before this - `db.connect()`'s `_migrate()` upgrades any row still carrying it.)

**Removing files is deliberately separate from removing data.** `kvittomall remove <row_key> [--only downloads|processed|final]` deletes an entry's on-disk file(s) - never the CSV, the DB row, or the entries list - and, unlike every other scoped command, always requires a row key (no bulk "wipe everything" mode). It needs no new fail-safe logic of its own: `drive.remove_downloads()`/`media.remove_processed()`/`pdf_gen.remove_final()` just delete the file and leave the DB exactly as it was, because `is_download_valid()`/`is_process_valid()`/`classify_generated()` already re-verify a file's presence on disk before ever trusting a recorded path - a later `download`/`process`/`generate` treats a manually-removed file exactly like any other accidental deletion and simply redoes that one piece of work.

**A CLI/web action can be scoped to one entry.** `download`, `process`, `generate`, `handled`, and `run` all accept an optional row_key (the row's stable `Tidstämpel`-based identity from `rowkey.row_key()`, *not* its CSV position, which isn't stable across re-fetches) to act on a single row instead of every row - see `cli.py`'s `SCOPABLE_STAGES` and each stage module's `run(only=...)` parameter. `fetch` is the one exception (it always pulls the whole sheet). A scoped `run <row_key>` skips `fetch` entirely. `remove` is scoped by design but intentionally left out of `SCOPABLE_STAGES`/`STAGES` (it takes an extra `--only` axis those don't). The local web UI (`kvittomall webui`, `kvittomall/web/`) is a thin control panel over these same functions - a dashboard with whole-pipeline buttons plus an `/entries` list/detail view for browsing and acting on individual rows, including per-row remove buttons - background-threaded so requests return immediately, still serialized through the same `run_lock()` every CLI invocation uses.

**PDF content is config-driven.** `kvittomall/config.py`'s `PDF_SECTIONS` (a list of `Section`/`Field` dataclasses) defines the cover page's layout - each `Field` maps a label to a sheet column and an optional value formatter (e.g. `currency()`/`mil()`, which append the unit *and* normalize the decimal separator to a comma, since Swedish convention differs from what a submitter might type). Changing what appears on the cover page means editing this structure, not `pdf_gen.py`'s rendering code. A `Field` with an empty label renders full-width with no bold prefix, for content that shouldn't look like a label/value pair - currently unused, but supported.

**The header logo can be SVG or a raster image, and the difference in output size is not subtle.** `config.LOGO` names the file (in the repo root, resolved to `paths.LOGO_PATH`); `pdf_gen._draw_page_header()` - called on *every* page, cover and attachments alike - checks the extension and renders it one of two ways. A `.svg` goes through `svglib`'s `svg2rlg()` (cached via `@lru_cache`, since re-parsing the file from disk on every page would be wasteful) and `reportlab.graphics.renderPDF`; anything else goes through the original `ImageReader`/`drawImage` path. This isn't a style choice: ReportLab embeds a raster image inefficiently (raw pixels through `FlateDecode` *and* `ASCII85Decode`, with no de-duplication across the separately-built pages that later get merged via pypdf), so the same logo redrawn on every page can multiply a receipt's file size several times over - a true vector SVG (not one that just wraps a raster image internally) avoids nearly all of that. Swapping the logo is just changing `config.LOGO` to a filename that exists in the repo root; nothing else needs to change.

**Image compression is a legibility-vs-size tradeoff, not baked in.** `config.IMAGE_QUALITY` names which tier is active - `"normal"` by default, overridable via `IMAGE_QUALITY` in `.env` through the same `_env()` pattern as the sheet columns. `media.py`'s `QUALITY_PRESETS` defines what each of the five names (`extreme`, `high`, `normal`, `low`, `potato`) actually means: a `QualityPreset(max_dimension, quality_steps, target_bytes, hard_ceiling, dimension_rounds)` - `encode_adaptive()` starts at the preset's highest quality step and only steps down (then shrinks dimensions, if still over `hard_ceiling`) as far as needed to fit `target_bytes`. `extreme` has `target_bytes=None`, so it always returns after a single high-quality pass with no resize - the point is legibility, not a polished photo, so even `normal` compresses harder than a typical image pipeline would. `media.py`'s `get_quality_preset()` is the one that validates `config.IMAGE_QUALITY` against the actual preset names (config.py just holds the configured string, since it doesn't know what's valid), raising `SystemExit` on an unrecognized value - resolved once per `process` run via the same "fail fast before doing any work" pattern as `drive.py`'s `_get_drive_service()`. Changing the setting only affects attachments processed *after* the change - already-processed files in `data/processed/` stay valid per the fail-safe checks above and aren't retroactively redone.

**Every sheet column name is configurable, not hardcoded.** `config.py` defines one named constant per column the pipeline actually reads (`TIMESTAMP_COLUMN`, `NAME_COLUMN`, `SUM_COLUMN`, `MIL_COLUMN`, `ROUTE_COLUMN`, etc.), each produced by `_column(env_var, default)` - the default matches the current Google Form's exact wording, but any of them can be overridden per-deployment with a `SHEET_COLUMN_*` variable in `.env`, since the Form's question wording can differ between committees without requiring a code change. `config.py` calls `load_dotenv()` at import time (not inside any one stage's `run()`), so this - and every other `.env`-driven setting read anywhere in the codebase - is guaranteed loaded regardless of which single stage gets invoked standalone. Only columns the pipeline actually reads get a constant; a column that exists in the sheet purely for the submitter's own record (e.g. `Godkännande`, a self-attestation checkbox) has no constant and is never touched by any code, by design - see `category_for()`'s docstring note distinguishing a column's header (has a constant) from the *values* inside it (matched literally in `CATEGORY_MAP`, which doesn't need one).

**Logging**: `kvittomall/logging_setup.py` gives every stage a logger writing to `logs/{stage}-{year}-{month}.log` (Swedish/`Europe/Stockholm` timestamps regardless of host timezone, monthly files so they don't grow forever). Console output is WARNING-and-above by design - routine progress is a live progress bar (`kvittomall/progress.py`), coordinated with the logging handler so a warning/error print doesn't get mangled mid-bar.

**`data/` (downloads/, processed/, responses.csv, kvittomall_state.db, the lock file), plus `final/`, `logs/`, `.env`, and any `*.json` (service account key), are all gitignored runtime state - none of it is precious.** `data/` holds everything the pipeline owns and rebuilds itself (see `paths.py`); it's kept separate from `final/` (the actual deliverable output) and `logs/` (kept easy to check without digging in), both of which stay in the repo root. The Google Sheet is the source of truth; any of this can be deleted and rebuilt with `python -m kvittomall run` (existing valid downloads/processed files get adopted rather than redone, per the fail-safe checks above).

## Module map

| Module | Responsibility |
|---|---|
| `paths.py` | All path constants, `ensure_dirs()` |
| `config.py` | Sheet column names (each overridable via `.env`), `PDF_SECTIONS`, category mapping, `load_dotenv()` |
| `rowkey.py` | Row identity, filename sanitization, content/link hashing, DB sync (incl. renaming files in place if a submitter's name changes) |
| `db.py` | Schema + all state read/write, including the fail-safe validity checks |
| `atomic.py` | `atomic_write()` |
| `lock.py` | Single-instance file lock for mutating commands |
| `google_api.py` | `ACCESS_MODE` handling, service-account credential/service builders, error-message translation - shared by `sheet.py` and `drive.py` |
| `sheet.py` | Stage 1 (fetch/validate CSV, via API or public export) + `read_rows()`, used by every later stage |
| `drive.py` | Stage 2 (download, via API or public link), per-attachment state, adopts pre-existing downloads |
| `media.py` | Stage 3 (adaptive JPEG compression via `IMAGE_QUALITY` presets / PDF passthrough), adopts pre-existing processed files |
| `pdf_gen.py` | Stage 4 (cover page + attachment merge) plus the `handled` review workflow (`toggle_handled`/`mark_all_handled`/`run_handled`) and `remove_final` |
| `status.py` | Read-only status report, incl. `row_status()` shared with the web UI |
| `cli.py` / `__main__.py` | Argument parsing and dispatch |
| `web/app.py` | Local web UI (`kvittomall webui`) - thin Flask control panel over the same stage functions, plus `/entries` list/detail views |
